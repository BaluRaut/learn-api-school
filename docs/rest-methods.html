🔧 Every REST method — the seven stamps

REST has exactly seven verbs you will use, and three words that tell them apart: safe (changes nothing), idempotent (doing it twice equals doing it once) and cacheable (the answer may be kept). This page is each method drawn against the school's counter, what it returns, what it must never do — and a script that proves every rule on the real API in the repo.

🧠 The three words

Safe — the request changes nothing on the server. A crawler, a prefetcher or a nervous user hitting refresh can never do harm. GET, HEAD, OPTIONS.
Idempotent — sending it N times leaves the same state as sending it once. Retries after a timeout are free. GET, HEAD, OPTIONS, PUT, DELETE — and POST only when you add an Idempotency-Key.
Cacheable — the response may be stored and reused by the browser, a CDN or a proxy. Only GET and HEAD in practice, controlled by Cache-Control and validated with ETag (lesson 10).
Why it matters: every intermediary on the internet — browsers, CDNs, proxies, retry libraries — trusts these words. A GET that deletes, or a PUT that is not idempotent, breaks them all at once.

🖼️ Each method, drawn against the counter

Dashed arrows are single messages. Each drawing shows the request the counter really accepts and the exact answer api/methods_demo.sh receives.

GET
Read it. The only method most of the internet ever uses. Never changes anything, so it may be repeated, cached, prefetched and bookmarked. Filters, sorting and paging travel in the query string, never in a body.
HEAD
GET without the body. Same status, same headers, zero bytes of payload. Link checkers, cache validators and download managers live on it. If you implement GET you get HEAD almost for free; do not forget it.
OPTIONS
What may I do here? Lists the allowed methods for a URL, and doubles as the browser's CORS preflight: before a cross-origin write, the browser asks OPTIONS first and only proceeds if the answer allows it. The UI school's lesson 11 is the other half of this story.
POST
Create a new one — or do a thing. The server chooses the new URL and answers 201 with a Location. Repeating it repeats the effect, so retries need an idempotency key. Also the home of actions that are not nouns: POST /students/6/promote.
PUT
Replace the whole thing. The client names the URL and sends the complete representation; whatever was there before is gone. Repeating it changes nothing further. A partial body is a bug in disguise: either a 400, or fields silently emptied.
PATCH
Change part of it. Send only the fields that change; the server merges and validates the result. Merge-patch is idempotent; a list of JSON-Patch operations may not be. Unknown fields must fail loudly, or clients will believe they saved something they did not.
DELETE
Remove it. After one DELETE or ten, the student is gone, which is what idempotent means. Whether the second call says 204 or 404 is a style choice; what matters is that it never fails a retry. Needs authentication, never a body, and 202 if the work is deferred.
TRACE · CONNECT
The two you meet but rarely write. TRACE is a diagnostic echo that most servers switch off for safety. CONNECT asks a proxy to open a raw tunnel, which is how HTTPS passes through corporate proxies. Know them for the exam; leave them to the infrastructure.

🧭 PUT vs PATCH vs POST — the short decision guide

Does the client know the URL of the thing?
No — the server must invent it → POST to the collection, answer 201 + Location. Add an Idempotency-Key so a retry cannot create twins.
Yes — is the client sending the whole thing?
  Yes → PUT. Missing fields are an error, not "keep the old value". Send If-Match to avoid overwriting someone else's edit.
  No, just some fields → PATCH with application/merge-patch+json. Reject unknown fields with 400.
Is it an action, not a document? ("promote", "send the report") → POST to a verb-shaped sub-resource, and say so in the docs. Never a GET.

🔬 Run it — every method against the real counter

api/methods_demo.sh sends all seven methods to api/school_api.py and prints the headers that prove each rule: the ETag on GET and HEAD, the Allow list on OPTIONS, two Locations from two POSTs, one student from two PUTs, a 400 for a partial PUT, a merged PATCH, and 204 twice for DELETE.
