🔀 Every API type — one school, many counters

The course builds one API: a REST counter (lessons 01–12). This page is the map of all the other shapes an API can take — what each one is, the school analogy, who starts the conversation, when it is right, and when it is the wrong tool. Six of them are runnable in this repo, serving the same five students, so you can compare the wire instead of the marketing.

🖼️ Every type, drawn — who talks to whom

One row per type, in the same reading order as the table: the left end asks, the right end answers, dashed arrows are single messages, solid arrows are an open line. Click a name in the table to jump here.

REST
Nouns in labelled cabinets. Resources live at URLs; GET/POST/PUT/DELETE are the verbs; the whole representation comes back, and caches can key on the URL. The shape this course builds.
JSON-RPC
"Do this thing", by name. One endpoint, a method name and params; the answer carries the same id. Errors travel inside the result, not as HTTP status. The MCP school speaks exactly this.
SOAP / XML-RPC
The notarised envelope. XML messages inside an envelope, described by a WSDL contract, with standards for signing, security and transactions. Heavy tooling; still mandatory in banking, telecom and government integrations.
GraphQL
One window, you write the form. A single endpoint and a query language: the client names exactly the fields it wants, the server resolves them from many sources and returns precisely that. No over-fetching; but caching and query cost become your problem.
gRPC
The typed internal hatch. A .proto file defines the calls; code is generated for every language; messages travel as compact binary over HTTP/2, with streaming both ways. Perfect between your own services; browsers need a proxy.
tRPC
One office, one language. The client calls server functions as if they were local, and TypeScript carries the types across the wire with no separate schema. Wonderful inside one codebase; anyone outside it must still be given REST or GraphQL.
OData
REST with a query language bolted on. Standard URL operators for filtering, selecting, sorting and paging over entity sets, plus metadata documents. Common in Microsoft ecosystems and reporting tools; rarely chosen for a new public API.
Long polling
The clerk holds your question. A normal request the server keeps open until there is news or a timeout, then the client immediately asks again. Works through any proxy and client; costs one held connection per client.
Server-Sent Events
The loudspeaker. One HTTP response that never ends; the server pushes small text frames down it, each with an id. Browsers reconnect automatically and resume from the last id. One-way only, and very cheap.
WebSocket
The open phone line. An HTTP request is upgraded into a persistent socket, and after that both sides send frames whenever they like. Chat, cursors, games, live dashboards. Overkill for plain request/response.
WebRTC
Desk to desk, directly. A server introduces two peers by exchanging offers and answers; after that audio, video and data flow between them directly. Video calls and huge peer transfers. Not for anything you want to control on a server.
Webhook
You leave your phone number. Register a URL once; when something happens, their server POSTs the event to you. Reverse of everything above. Sign it, verify it, and make the handler idempotent because deliveries repeat.
Queue · AMQP / SQS
The pigeonhole, one reader. A producer drops a job; a broker routes it to a queue; exactly one worker takes it and acknowledges it. Retries, dead-letter queues and backpressure come built in. AMQP (RabbitMQ) and SQS are the common dialects.
Event stream · Kafka
The logbook everyone replays. Producers append to a partitioned log; every consumer keeps its own place in it and may re-read from the start. Many readers, audit trails, replay after a bug. Heavier to run than a queue.
MQTT
The school PA system, for tiny devices. Publish/subscribe through a broker on named topics, with headers of a couple of bytes and three delivery guarantees. Built for sensors, phones and unreliable networks. Not a request/response tool.
Batch / file transfer
The nightly van. A schedule drops a file on a shared location and another system picks it up hours later. Still how banks, payroll and retail move millions of rows. Fine when nobody is waiting; wrong for anything a person is.
Library / SDK
The tool in your own bag. A package exposes functions to your code; you call them and get a value or an exception back, in the same process. The oldest kind of API, and versioning, docs and deprecation apply to it exactly as to a counter.
System call
Asking the building manager. Programs cannot touch files, memory or the network themselves; they ask the operating system through a fixed set of calls and get back a descriptor or an error number. Every network API on this page bottoms out here.
Database driver
The wire to the record room. A driver speaks the database's own protocol so your code can send SQL and read rows back through a cursor. It is an API too, and the one you must never expose directly: put a counter in front of it.
Device / hardware
The socket in the wall. Cameras, GPS, USB, Bluetooth and GPIO pins are reached through APIs the operating system or browser mediates, usually behind a permission prompt. Same contract idea, with a human in the loop.

1 📨 Ask & answer — the request/response family

You ask, it answers, the conversation is over. Three sub-shapes: nouns (REST), verbs (RPC) and "you write the answer's shape" (GraphQL).

In this course: REST is lessons 03–12; the others are lesson 11. In the family: the MCP school is a JSON-RPC protocol end to end.

2 📡 Stay on the line — streaming and realtime

One connection, many messages. The difference between them is who may speak, and how long the line stays open.

Cost to remember: every open connection is memory and a file descriptor on the server — 10,000 idle sockets is an architecture decision, not a detail. Load balancers and proxies need to be told to allow them.

3 📬 Leave a message — asynchronous and decoupled

Nobody waits for an answer. The producer is done when the message is accepted; the work happens later, possibly somewhere else, possibly twice.

The rule that saves you: at-least-once delivery means duplicates. Make every handler idempotent (lesson 07) and the whole family becomes safe.

4 🧰 No network at all — the APIs most people forget

"API" is older than the web. A library, a system call, a database driver and a device interface are all contracts between two pieces of software — and the lessons of this course apply to them unchanged.

🌍 The other way to classify: who is allowed to call it

Type answers "what shape?". Audience answers "what are the rules?" — and audience usually decides more of your work than shape does.

🧭 Which one? — the short decision guide

Start here: is a human waiting for the answer?
No → asynchronous. One known consumer → a queue. Many consumers or replay → an event stream. Somebody else's system that must be told → a webhook. Millions of rows overnight → batch file.
Yes → is the update continuous?
  Yes, one way → SSE. Both ways → WebSocket. Media or peer-to-peer → WebRTC. Ancient clients or hostile proxies → long polling.
  No → who calls it? Public/partner → REST (cacheable, documented, boring — the right answer far more often than it is exciting). Your own services, chatty and typed → gRPC. One UI needing many shapes → GraphQL. One TypeScript codebase → tRPC. An enterprise that requires it → SOAP.
And always: the shapes compose. A REST counter that enqueues a job, finishes with a webhook, and streams progress over SSE is not three architectures — it is one, using each family for what it is good at.

🔍 What to notice, in order: REST hands back whole resources; JSON-RPC returns an error inside a 200; GraphQL returns exactly the fields you named; long polling answers late, once; SSE keeps one connection and frames each event with an id the browser replays via Last-Event-ID; the WebSocket upgrades with 101 Switching Protocols and then either side may speak. Same data, six wires.

🧪 Nine ways to test a counter — the API testing types

Whatever its type, an API is tested the same nine ways. Each row says what the test asks, and how you would run it against this counter. Lesson 12 builds the first three; the rest are the production habits.

Smoke testing
Flick every switch once. Start the counter, hit each endpoint with one known-good request, expect the happy status codes. Here it is api/smoke_test.sh: 12 labelled checks in curl, one per lesson — the CI/CD school runs it on every push.
Functional testing
Does it do what the spec says? Each requirement becomes a case with an expected answer: a duplicate email returns 409, a missing key returns 401, the error shape is always the same. Compare result to expectation, every rule.
Integration testing
Several calls, one story. Enrol a student, read them back, update them, delete them, confirm the 404: the calls depend on each other and on real neighbours (the database, a webhook receiver). Where most production bugs actually live.
Regression testing
Did the change break what already worked? Run the same inputs against the old and the new build and diff the answers. Recorded responses become the expected results; a changed field that nobody meant to change fails the build.
Load testing
What is the capacity? Simulate the traffic you expect (and a bit more) with a load tool, and watch latency percentiles, error rate and the rate limiter. The number you learn is the one autoscaling and the on-call runbook depend on.
Stress testing
Push until it breaks, on purpose. Far beyond expected load, to see the failure mode: polite 429s and a queue, or timeouts and a crash? And whether it recovers by itself when the flood stops. Breaking is fine; breaking badly is the finding.
Security testing
Every door, every lock. Try to get in without a hall pass, with someone else's pass, with injection in every field, with too many requests. Check what is logged. The OWASP API Top 10 is the checklist; the answer must always be a polite refusal.
UI testing
Through the notice board. A real browser fills the form; the UI calls the counter; the test asserts what the person sees. Finds the bugs that live between the two schools: CORS, a renamed field, a loading state that never ends.
Fuzz testing
Feed it nonsense until it flinches. Generate random and malformed inputs — empty, huge, wrong types, unicode — and send thousands. Any 500, hang or crash is a finding; a 400 with the standard error shape is the counter doing its job.
🧭 Order of adoption: smoke on every push → functional for every rule in the spec → integration for the stories that matter → regression by diffing recorded answers → load once before launch and after every big change → security before anything is public → fuzz whenever you touch a parser → stress when you need to know the failure mode → UI through the notice board, a few golden paths.
