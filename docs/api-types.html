1 📨 विचारा आणि उत्तर घ्या — request/response कुटुंब

तुम्ही विचारता, ते उत्तर देते, संवाद संपला. तीन उप-आकार: नामे (REST), क्रियापदे (RPC) आणि "उत्तराचा आकार तुम्ही लिहिता" (GraphQL).

या कोर्समध्ये: REST म्हणजे धडे 03–12; बाकीचे धडा 11. याच कुटुंबात: MCP शाळा हा टोकापासून टोकापर्यंत JSON-RPC प्रोटोकॉल आहे.

2 📡 लाइनवर रहा — streaming आणि realtime

एक जोडणी, अनेक संदेश. त्यांच्यातला फरक म्हणजे कोण बोलू शकतो, आणि लाइन किती वेळ उघडी राहते.

लक्षात ठेवायचा खर्च: प्रत्येक उघडी जोडणी म्हणजे server वरची memory आणि एक file descriptor — 10,000 निष्क्रिय sockets हा रचनेचा निर्णय आहे, तपशील नव्हे. Load balancers आणि proxies ना ते परवानगी द्यायला सांगावे लागते.

3 📬 निरोप ठेवा — asynchronous आणि सुटे

उत्तरासाठी कोणीच थांबत नाही. संदेश स्वीकारला की producer चे काम संपले; प्रत्यक्ष काम नंतर होते, कदाचित दुसरीकडे, कदाचित दोनदा.

तुम्हाला वाचवणारा नियम: किमान-एकदा पोहोच म्हणजे दुहेरी संदेश. प्रत्येक handler idempotent करा (धडा 07) आणि अख्खे कुटुंब सुरक्षित होते.

4 🧰 Network अजिबात नाही — बहुतेकांना विसरलेले API

"API" हे web पेक्षा जुने आहे. Library, system call, database driver आणि device interface — हे सगळे दोन सॉफ्टवेअरमधले करारच आहेत; आणि या कोर्सचे धडे त्यांना जसेच्या तसे लागू होतात.

🌍 वर्गीकरणाचा दुसरा मार्ग: कोणाला कॉल करायची परवानगी आहे

🧭 कोणता? — छोटे निर्णय-मार्गदर्शन

Start here: is a human waiting for the answer?
No → asynchronous. One known consumer → a queue. Many consumers or replay → an event stream. Somebody else's system that must be told → a webhook. Millions of rows overnight → batch file.
Yes → is the update continuous?
  Yes, one way → SSE. Both ways → WebSocket. Media or peer-to-peer → WebRTC. Ancient clients or hostile proxies → long polling.
  No → who calls it? Public/partner → REST (cacheable, documented, boring — the right answer far more often than it is exciting). Your own services, chatty and typed → gRPC. One UI needing many shapes → GraphQL. One TypeScript codebase → tRPC. An enterprise that requires it → SOAP.
And always: the shapes compose. A REST counter that enqueues a job, finishes with a webhook, and streams progress over SSE is not three architectures — it is one, using each family for what it is good at.

🔬 त्यांपैकी सहा चालवा — तेच पाच विद्यार्थी, सहा आकार

api/api_types.py is one zero-dependency server that answers about the same data as REST, JSON-RPC, GraphQL, long polling, SSE and a real WebSocket (handshake and frames included, ~160 lines). api/types_client.py exercises all six and prints every byte.

python3 api/api_types.py        # terminal 1
python3 api/types_client.py     # terminal 2

⚠️ चुकीचा प्रकार निवडायला लावणाऱ्या चुका

चूकप्रत्यक्षात काय होतेत्याऐवजी हे करा
लोकप्रियतेनुसार निवडणे ("सगळे GraphQL वापरतात")दोन endpoints च्या service साठी query-खर्चाच्या मर्यादा, cache ची गुंतागुंत आणि schema ची टीम वारशाने मिळतेआधी पाच अक्षांवर ठेवा; कंटाळवाणे REST श्रेय मिळते त्यापेक्षा जास्त वेळा जिंकते
क्वचित घडणाऱ्या events साठी दर काही सेकंदांनी pollingहजारो रिकामी उत्तरे, आणि तरी उशीरwebhook (ते तुम्हाला कॉल करतात) किंवा SSE (एक उघडी लाइन)
request/response साठी WebSocketids, पुन्हा-प्रयत्न, timeouts आणि caching तुम्ही हाताने पुन्हा बांधता — वाईट रीतीनेसाधे HTTP; socket खऱ्या दुहेरी कामासाठी ठेवा
थेट browsers ला gRPCशेवटी REST किंवा gRPC-Web proxy लिहून चालवावाच लागतोकाठावर REST/JSON, services मध्ये gRPC
कॉल करणाऱ्याला उत्तर हवे असताना queuesynchrony चे नाटक करायला status-polling endpoint शोधावा लागतोsynchronously उत्तर द्या; फक्त हळू भाग रांगेत टाका
स्वाक्षरी किंवा idempotency शिवाय webhooksबनावट events, आणि दुहेरी संदेश दोनदा लागूpayload वर स्वाक्षरी करा, ती तपासा, event id नुसार दुहेरी काढा
