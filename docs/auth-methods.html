🪪 Every way to show a hall pass — REST API authentication methods

Authentication answers "who is asking?"; authorization answers "what may they do?". Every method below is a different way to answer the first question — from a password on every request to a certificate at the door. Eleven flows drawn against the school's counter, when each is right, what goes wrong, and seven of them runnable in this repo, all guarding the same grades.

🚦 401 vs 403 — the two refusals

401 Unauthorized really means unauthenticated: "I cannot tell who you are." It must carry a WWW-Authenticate challenge that says how to identify yourself (Basic realm="school", Bearer error="invalid_token"…).
403 Forbidden means "I know exactly who you are, and the answer is no": a student asking to delete grades.
An unknown API key is the grey zone. Strictly it is a 401 (the server cannot tell who holds it — Stripe and GitHub answer 401); the counter in lesson 06 answers 403 ("a pass, but not the right one"). Both are seen in the wild; the demo below does it the strict way, and shows the textbook 403 with roles.

🖼️ Each method, drawn

Dashed arrows are single messages, solid arrows are a handshake. Each drawing shows the exact header the method puts on the wire and the answer the counter gives.

Basic
The pass you re-show at every door. Username and password, base64-encoded, sent with every request. Trivial to implement, built into every HTTP client, and only ever acceptable over HTTPS. Nothing to revoke except the password itself.
API key
A program's hall pass. A long random string that identifies an application, not a person, sent in a header. Perfect for server-to-server and for metering. Weak on its own: no expiry unless you rotate, no user, and fatal if it leaks into a browser or a URL.
Bearer token (opaque)
Log in once, get a wristband. Credentials are exchanged once for a random token; every later request carries the token. The server looks it up, so it can expire it, scope it and revoke it instantly. One extra lookup per request is the price.
JWT
A signed wristband. Header, payload and signature, base64-joined by dots. Any server holding the key verifies it without a database, which is why it scales across services. The payload is readable, so it carries claims, never secrets; and it stays valid until it expires, so keep that short.
Session cookie
The browser's way. After login the server sets a cookie; the browser stores it and sends it back on every request without any code. The three flags do the security work. Behind it sits a session table, so log-out and revocation are instant.
OAuth 2.0 (authorization code + PKCE)
Delegation without sharing the password. The person logs in at the authorization server and consents; your app receives a short code, exchanges it (with a PKCE verifier) for an access token, and calls the API with that. Scopes limit what the token may do; refresh tokens renew it. The standard for third-party access.
OpenID Connect
"Sign in with Google" — OAuth plus identity. OAuth answers "may this app act?"; OpenID Connect adds an ID token that answers "who is this person?", signed by the identity provider. Verify its signature, issuer, audience and expiry. Never treat a bare access token as proof of identity.
OAuth client credentials
A program's own door. No person is involved: the program sends its client id and secret (as a form, or as Basic) to the token endpoint and gets a short-lived, scoped access token. The default OAuth grant for service-to-service and partner integrations; what a stolen token can do is bounded by its scope, not by who holds it.
OAuth device code
A door for things without a keyboard. The TV or command-line tool shows a short code; the person approves it on a phone or laptop; the device keeps polling the token endpoint until the answer changes from "pending" to a token. How gh auth login and smart TVs sign in (RFC 8628).
HMAC request signing
Sign the request itself. Both sides hold a secret; the sender signs method, path, time and body; the receiver recomputes and compares. Nothing secret crosses the wire, tampering shows, and the timestamp defeats replays. How webhooks are verified and how AWS signs every call.
Mutual TLS
Both sides show ID before the door even opens. Ordinary TLS proves the server; mutual TLS makes the client present a certificate too, checked against a trusted authority during the handshake. The strongest machine-to-machine proof, and the most operational work: issuing and rotating certificates.

🎫 OAuth 2.0 grant types — which door for which caller

"OAuth" is not one flow. The grant_type a client sends to the token endpoint says who is asking and how they prove it. Two grants cover almost everything today; two you will still meet in old code are gone.

🎫 The rule of thumb: a person in a browser → authorization_code + PKCE; a program on its own → client_credentials; keep either alive with refresh_token; a screen without a keyboard → device code. If a library or a tutorial reaches for password or implicit, it is older than OAuth 2.1 — the token endpoint in this repo refuses both with unsupported_grant_type.

🧭 Which one? — the short decision guide

A browser app on your own site → session cookie (HttpOnly, Secure, SameSite) — or a Bearer token if the front end is a separate origin.
A person signing in with an existing account → OpenID Connect through a provider; verify the ID token.
A third-party app acting for a user → OAuth 2.0 authorization code with PKCE, narrow scopes, short access tokens, refresh tokens.
Your own services calling each other → mTLS (or a service mesh doing it for you); otherwise OAuth client_credentials from a shared authorization server, or JWTs signed by an internal issuer.
A partner's server calling your API → OAuth client_credentials with narrow scopes, or an API key plus HMAC signing (or mTLS) for integrity; rotate on a schedule.
You calling a webhook receiver → sign the payload (HMAC) with a timestamp; the receiver verifies before trusting a byte.
A quick script against an internal tool → Basic over HTTPS is honest and fine — just not for the public.
Always: authentication says who; authorization (roles, scopes, object ownership) says what — check both on every request, and answer 401 or 403 precisely.

🔬 Run seven of them — the same grades, seven hall passes

api/auth_demo.py guards one resource seven ways — Basic, API key, opaque Bearer token, JWT (HS256, signed and verified with the standard library), HMAC request signing, a session cookie, and an OAuth 2.0 token endpoint (client_credentials and refresh_token, the password grant refused) — with a proper WWW-Authenticate on every 401 and a real 403 for a student who tries to delete. api/auth_client.py shows every header on the wire, an expired token, a forged JWT, a tampered signature, a replayed request, and a scoped token refused a DELETE with insufficient_scope.

python3 api/auth_demo.py         # terminal 1
python3 api/auth_client.py       # terminal 2

What you should see (token values differ each run):

── 1 Basic — the pass you re-show at every door (user:password, base64, on EVERY request)
   no header                                      → 401  send Authorization: Basic base64(user:password)   WWW-Authenticate: Basic realm="school"
   Authorization: Basic dGVhY2hlcj…               → 200  as teacher (teacher) via basic · 2 grades
   wrong password                                 → 401  wrong user or password   WWW-Authenticate: Basic realm="school"
   base64 is NOT encryption — Basic is only ever acceptable over HTTPS

── 2 API key — a program's pass; no person behind it (the counter's X-API-Key, lesson 06)
   no key                                         → 401  no X-API-Key header   WWW-Authenticate: ApiKey realm="school", header="X-API-Key"
   X-API-Key: hall-pass-123                       → 200  as counter-bot (teacher) via apikey · 2 grades
   X-API-Key: made-up                             → 401  unknown key — we cannot tell who you are   WWW-Authenticate: ApiKey realm="school", header="X-API-Key"
   an unknown key = we cannot tell who you are = 401 (strict); the lesson-06 counter says 403 — both are seen in the wild

── 3 Bearer token (opaque) — log in once, get a wristband, show the wristband
   POST /login teacher/chalk                      → 200  token W-TTEyrfwc… expires_in 3600
   no token                                       → 401  send Authorization: Bearer <token>   WWW-Authenticate: Bearer realm="school"
   Authorization: Bearer W-TTEyrfwc…              → 200  as teacher (teacher) via token · 2 grades
   a token issued with ttl=1, 1.2 s later         → 401  token expired   WWW-Authenticate: Bearer realm="school", error="invalid_token", error_description="expired"
   DELETE as student (valid token)                → 403  student is a student: may read grades, not delete them
   401 = who are you? · 403 = I know exactly who you are, and no · the server LOOKS UP each opaque token

── 4 JWT — a SIGNED wristband: the server verifies, it does not look anything up
   header  {'alg': 'HS256', 'typ': 'JWT'}
   payload {'sub': 'teacher', 'role': 'teacher', 'iat': 1790052651, 'exp': 1790056251}   ← readable by anyone; never put secrets in it
   Authorization: Bearer eyJhbGciOiAiSF…          → 200  as teacher (teacher) via jwt · 2 grades
   payload edited to role=headmaster, same signature → 401  JWT bad signature   WWW-Authenticate: Bearer realm="school", error="invalid_token", error_description="bad signature"
   the signature pins the payload; expiry is inside it (exp) — and a stolen JWT is valid until then, so keep them short

── 5 HMAC request signing — you sign the request itself (webhooks, AWS SigV4 style)
   unsigned                                       → 401  sign the request: X-Key-Id, X-Timestamp, X-Signature   WWW-Authenticate: HMAC-SHA256 realm="school", headers="X-Key-Id X-Timestamp X-Signature"
   X-Key-Id key-1 · X-Timestamp 1790052651 · X-Signature 2370b654… → 200  as key key-1 (teacher) via hmac · 2 grades
   same signature, path changed by an attacker    → 401  signature does not match — the request was altered or the secret is wrong   WWW-Authenticate: HMAC-SHA256 realm="school", headers="X-Key-Id X-Timestamp X-Signature"
   valid signature, 15-minute-old timestamp (replay) → 401  timestamp outside the 5-minute replay window   WWW-Authenticate: HMAC-SHA256 realm="school", headers="X-Key-Id X-Timestamp X-Signature"
   the secret never travels; the signature covers method + path + time + body, so nothing can be altered or replayed

── 6 Session cookie — the browser's way: log in, the server sets an HttpOnly cookie, the browser sends it back
   no cookie                                      → 401  no valid session cookie — POST /login first   WWW-Authenticate: Cookie realm="school"
   POST /login                                    → 200  Set-Cookie: sid=Zha4S2aRtC…; HttpOnly; SameSite=Lax
   GET with the cookie jar                        → 200  as teacher (teacher) via session · 2 grades
   HttpOnly = JavaScript cannot read it (XSS cannot steal it) · SameSite = other sites cannot ride it (CSRF)

── 7 OAuth 2.0 client_credentials — a PROGRAM's own door: id + secret → access token, at the token endpoint
   POST /token grant_type=client_credentials (form) → 200  {access_token: _qxFCGv9…, token_type: Bearer, expires_in: 900, scope: grades:read}   Cache-Control: no-store
   GET /oauth/grades · Bearer _qxFCGv9…           → 200  as report-bot (client:grades:read) via oauth · 2 grades
   DELETE with scope=grades:read                  → 403  insufficient_scope   WWW-Authenticate: Bearer realm="school", error="insufficient_scope", scope="grades:write"
   wrong client_secret                            → 401  invalid_client   WWW-Authenticate: Basic realm="token endpoint"
   grant_type=password                            → 400  unsupported_grant_type: 'password' is not offered: people use authorization_code + PKCE, programs use client_credentials
   grant_type=refresh_token                       → 200  new access_token Ka1rN5IR… (the old refresh token is now used up)
   the shape every OAuth server speaks: a FORM to /token, a JSON {access_token, token_type, expires_in, scope} back, errors as {error} — and scope, not identity, decides the 403

MistakeWhat actually happensDo instead

Secrets inside a JWT payloadthe payload is base64, readable by anyone holding the tokenclaims only (sub, role, exp); secrets stay on the server
