⏮️ Before & trade-offs

Every tool replaced something worse — and is itself the wrong tool somewhere. For each big idea: what life was like before, honest merits ✅ / demerits ❌, and where to use it 👍 vs not 👎.

🗄️ REST (vs GraphQL, gRPC) — lessons 03, 11

⏮️ Before REST won (2000s)

Every service invented its own remote-call style: SOAP envelopes, custom XML, RPC verbs like getStudentById in the URL. Caches could not help, every client needed a special library, and 'the API' was a 40-page PDF.

✅ Merits

  • nouns + standard verbs: any HTTP client works, caches understand it
  • status codes and headers already mean things
  • easy to document (OpenAPI) and to mock

❌ Demerits

  • many round trips for a screen that needs five resources
  • over-fetching: the whole drawer when you wanted one field
  • 'RESTful' is a spectrum — teams argue about purity

👍 Use when

  • public and partner APIs, anything cacheable
  • CRUD over clear resources

👎 Think twice when

  • one UI needs many shapes of the same data → GraphQL
  • chatty, typed, internal service-to-service → gRPC

🪪 API keys vs bearer tokens vs OAuth — lesson 06

⏮️ Before standard passes

Passwords in query strings, shared 'admin' secrets pasted into every script, and no way to revoke one client without breaking all of them.

✅ Merits

  • API key: simplest machine pass, per-app, revocable
  • JWT: self-contained, expiring, signed — no lookup per request
  • OAuth/OIDC: users grant scoped access without sharing passwords

❌ Demerits

  • keys leak (logs, URLs, repos) and never expire on their own
  • JWTs cannot be un-issued before expiry without a deny-list
  • OAuth flows are real engineering; easy to misconfigure redirects

👍 Use when

  • keys for server-to-server, scoped and rotated
  • tokens for user sessions; OAuth when a third app acts for a user

👎 Think twice when

  • a key in a browser app — it is public the moment it ships
  • hand-rolled crypto or session logic — use the standard

📚 Cursor vs offset pagination — lesson 08

⏮️ Before pagination

'Return everything' — fine for 50 rows, fatal at 50,000: timeouts, memory, and clients that show a spinner forever.

✅ Merits

  • cursor: stable under inserts, fast with an index, the modern default
  • offset: trivial to implement, jump to page N

❌ Demerits

  • cursor: no 'page 7 of 40', opaque tokens to explain
  • offset: skips/duplicates when rows change; deep pages get slow

👍 Use when

  • cursor for feeds, logs, anything that grows
  • offset for small admin tables with a page picker

👎 Think twice when

  • offset on a table that grows while people scroll
  • cursor when the product genuinely needs 'jump to page 12'

🔢 Versioning in the path vs headers — lesson 09

⏮️ Before versioning

Changing a field renamed broke every client at once — or nothing ever changed because nobody dared.

✅ Merits

  • /v1 in the path: visible, cacheable, easy to route at the gate
  • header/media-type versions: one URL, cleaner resources

❌ Demerits

  • path versions multiply URLs and tempt big-bang rewrites
  • header versions are invisible in logs and links
  • every version you keep is a version you must test

👍 Use when

  • path versions for public APIs; additive changes on the same version
  • a written deprecation policy with dates and metrics

👎 Think twice when

  • versioning per field or per endpoint — chaos
  • breaking clients silently 'because it's cleaner'

⏱️ Rate limiting — lesson 10

⏮️ Before limits

One runaway script could empty the office: every visitor waited, and the fix was a phone call.

✅ Merits

  • fairness: one noisy client cannot starve the rest
  • a clear signal (429 + Retry-After) clients can obey
  • protects the record room and your bill

❌ Demerits

  • honest bursts get refused too — size the bucket for real use
  • limits per IP punish everyone behind one NAT
  • needs shared state across servers (the gateway's job)

👍 Use when

  • any public endpoint; anything a bug could hammer
  • per-key limits tied to plans

👎 Think twice when

  • internal calls between your own services with no budget problem
  • as a substitute for fixing an N+1 loop in the client

📣 Webhooks vs polling — lesson 11

⏮️ Before webhooks

Clients asked 'anything new?' every few seconds — thousands of empty answers, and still late.

✅ Merits

  • events arrive when they happen; zero wasted slips
  • one registration replaces a polling loop

❌ Demerits

  • you must run a reachable receiver (and secure it)
  • delivery can fail: retries, ordering and duplicates are your problem
  • debugging means two systems' logs

👍 Use when

  • 'tell me when' relationships: payments, CI results, enrolments
  • integrations with partners who cannot poll you at scale

👎 Think twice when

  • your consumer cannot expose a URL — use a queue or long polling
  • strict ordering or exactly-once — use an event log

🚪 API gateway — lesson 12

⏮️ Before gateways

Every API re-implemented auth, rate limits, TLS, logging and routing — five copies, five bugs.

✅ Merits

  • one place for auth, limits, routing, TLS, logs, WAF
  • APIs stay small; policies change without redeploys
  • managed versions exist (AWS API Gateway, Kubernetes Ingress + plugins)

❌ Demerits

  • another hop, another thing to run and pay for
  • config sprawl; a gateway outage is everyone's outage
  • easy to hide business logic where it doesn't belong

👍 Use when

  • more than one API, any public exposure, per-client plans
  • you need central auth/limits/observability

👎 Think twice when

  • one internal service behind a VPN — a library may do
  • putting transformations and business rules in the gate
